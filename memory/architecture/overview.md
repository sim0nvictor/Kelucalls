# Kelucalls Architecture Overview

> High-level architecture and system boundaries for the Kelucalls platform.

## Purpose

Kelucalls is a crypto-call intelligence platform.

It monitors Telegram channels, extracts token calls, tracks their performance, calculates rankings and trends, and presents the results through:

- Web dashboard
- Telegram bot
- User notifications

This document describes the major components, their relationships, data flow, external services, and important operational rules.

It is intentionally high-level.

Detailed implementation knowledge belongs in the relevant architecture, feature, integration, fix, and decision documents.

---

# High-Level Architecture

```mermaid
flowchart LR
    TG[Telegram Channels] --> SCRAPER[GramJS Scraper]

    SCRAPER --> DB[(Supabase Postgres)]

    DB --> PRICE[Price Worker]
    PRICE --> DEX[DexScreener]
    PRICE --> DB

    DB --> ANALYTICS[Trending / Analytics Workers]
    ANALYTICS --> DB

    DB --> WEB[Next.js Web App]
    DB --> BOT[Telegraf Telegram Bot]
    DB --> ALERTS[Alert Workers]

    ALERTS --> DB
    DB --> BOT
    DB --> WEB
````

```text

       │                Call Metrics

       │              Trending / KeluScore
```

# 2. Telegram Scraper

**Location:** `index.js`

The scraper is responsible for ingesting Telegram channel activity.

It uses **GramJS** as a Telegram user client.

## Message Processing Flow

```text
Telegram Message
       │
       ▼
Message Parser
       │
       ▼
Chain / Contract Detection
       │
       ▼
Token Upsert
       │
       ▼
Call Insertion
       │
       ▼
Initial Price Lookup
       │
       ▼
Call Metrics
```

## Responsibilities

The scraper:

* Reads tracked channels from Supabase.
* Backfills recent messages on startup.
* Watches new Telegram messages.
* Detects Solana formats.
* Detects EVM formats.
* Detects Sui formats.
* Detects Tron formats.
* Supports other recognized chain formats.
* Extracts token symbols.
* Extracts contract addresses.
* Extracts GMGN links.
* Extracts DexScreener links.
* Extracts Pump.fun links.
* Processes new tracking requests.

## Telegram Authentication

Authentication is generated by:

```text
login.js
```

The scraper should use the dedicated:

```text
TELEGRAM_SCRAPER_SESSION
```

Telegram scraper sessions must remain separate from sessions used for web lookups or other Telegram functionality.

**Location:** `bot`

The Telegram bot uses **Telegraf**.

## Responsibilities

The bot:

* Registers Telegram users.
* Manages subscriptions.
* Manages alert preferences.
* Provides commands such as:

  * `/topkols`
  * `/trending`
  * `/list`
* Polls `bot_events`.
* Sends call alerts.
* Sends milestone alerts.
* Sends trending alerts.
* Sends coordinated-call alerts.

## Bot Event Flow

```text
Worker
   │
   ▼
bot_events
   │
   ▼
Bot Event Poller
   │
   ▼
Subscriber Filtering
   │
   ▼
Telegram Notification
```

The bot therefore consumes processed events rather than independently recreating the analytics pipeline.

Alert generation should remain separated from presentation.

# Operational Rules

## Telegram Sessions

Use separate Telegram sessions for:

* Scraper
* Web lookups

The scraper requires:

```text
TELEGRAM_SCRAPER_SESSION
```

Do not reuse Telegram sessions across unrelated services without understanding the authentication and operational consequences.

---

## Secrets

Never commit:

```text
.env
```

Never expose:

* Service-role keys
* API keys
* Telegram credentials
* Private tokens
* Authentication secrets

Environment variables may be referenced by name in documentation, but their values must never be stored in repository documentation or memory.

---

## Precomputed Intelligence

KeluScore and AI summaries are precomputed by workers.

Pages should consume stored results.

Avoid moving expensive scoring or AI generation into request-time page rendering unless the architecture is deliberately changed and documented.

---

## Scraper Concurrency

Multiple scraper instances may duplicate tracking-request processing because queue claiming is not atomic.

This is a known operational limitation.

Do not assume that running multiple scraper instances automatically provides safe distributed queue processing.

Any attempt to change this behavior should account for atomic claiming and concurrency.

---

## Raw Telegram Message Persistence

Raw Telegram message persistence should be verified before relying on replay functionality.

Do not assume that historical message replay is available merely because the scraper can process live messages.

---

## Tracking Requests

Check migration/code consistency around:

```text
tracking_requests
```

Field names and status values may currently differ between migrations and application code.

Before changing this subsystem:

1. Inspect current migrations.
2. Inspect current application queries.
3. Inspect the actual expected status values.
4. Verify consistency before making changes.

# Architectural Principles

## 1. Ingest Once, Process Centrally

Telegram data should enter the system through the ingestion layer and then be persisted for downstream processing.

Avoid having individual consumers independently scrape or reconstruct the same source data.

---

## 2. Persist Derived Intelligence

Important derived intelligence should be persisted when it is expensive or computationally significant.

Examples:

* Call metrics
* Channel statistics
* Trending data
* KeluScore
* Intent signals
* AI summaries

This allows the web application and bot to consume consistent results.

---

## 3. Separate Ingestion, Processing, and Presentation

The architecture broadly follows:

```text
Ingestion
    ↓
Persistence
    ↓
Processing
    ↓
Analytics
    ↓
Presentation / Notifications
```

This separation allows individual services to evolve independently.

---

## 4. Protect Historical Data

Kelucalls tracks historical call performance.

Changes involving:

* Calls
* Tokens
* Call metrics
* Prices
* ROI
* Milestones
* Rankings
* Aggregated statistics

must consider their effect on historical results.

Do not casually rewrite historical data.

---

## 5. Prefer Existing Abstractions

Before introducing a new:

* API client
* Database client
* Analytics calculation
* Worker utility
* Telegram integration
* Formatting utility

search the existing repository and memory system first.

# Known Architectural Risks

The following risks are currently documented by the project architecture.

### Non-atomic tracking-request processing

Multiple scraper instances may process the same tracking request because queue claiming is not atomic.

### Telegram replay dependency

Replay functionality depends on reliable raw Telegram message persistence.

### Migration/code drift

`tracking_requests` may currently have inconsistencies between migration definitions and application expectations.

These should be treated as known architectural concerns rather than silently worked around.
